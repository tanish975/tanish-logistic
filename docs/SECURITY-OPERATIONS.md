# Security operations and release checklist

This is a source-code hardening pass, not a guarantee of security, a penetration test of production, or a compliance certification. The application and infrastructure still require the actions below. The changes have **not** been deployed or applied to a live database as part of this work.

## Immediate action: previously public data

This repository is public. Unused legacy booking, driver, vehicle, payment and user JSON exports (including a password hash) were removed from the current tree, but **remain in existing Git history, clones, caches and backups**. Removing a file in a new commit does not erase its history. The local copies were left in place and ignored.

1. Identify whether any exported records or credentials were real. Rotate every matching account password and any related credentials, using the appropriate service's normal recovery procedures; also review the database and email-provider credentials for exposure. Disabling old accounts may be appropriate.
2. Review the privacy impact of the historic records, retention and any notification obligations. Restrict repository access if appropriate.
3. A history rewrite and coordination with collaborators, forks, backups and hosting providers require a separate approved plan. Do not force-push or assume that a rewrite removes all public copies.

## Before deploying this release

1. **Back up and rehearse the database changes.** The new migration adds `User.sessionVersion`, `SiteSettings`, review storage and booking columns missing from the old migration history. Earlier migrations include destructive changes and may not match databases altered using `db push`. Inspect the actual schema and `prisma migrate status`, compare migration history to a disposable clone, rehearse restoration and migration, then apply only an explicitly reviewed plan. `IF NOT EXISTS` does not repair incompatible existing column types or an unbaselined history. Never use `db push --accept-data-loss` as an emergency shortcut.
2. **Plan the sign-in change.** Old cookies are intentionally invalidated by this release. Accounts must sign in again after the schema is migrated. The app checks the current database role and session version on every protected request; the encrypted session expires after eight hours. Sign-out revokes all sessions for that account using an atomic version increment. Normal Prisma user updates also invalidate old sessions through `updatedAt`. If changing passwords directly with SQL or another tool, increment `sessionVersion` and update `updatedAt` in the same transaction. If database revocation fails, the UI reports local sign-out only and warns that other sessions may remain valid.
3. **Protect administrator access beyond the application.** The app has password authentication but **does not implement MFA**. Enable MFA for GitHub, Vercel, database and email-provider accounts; add an MFA-capable access gateway or identity provider for the admin surface. Consider an IP allowlist or equivalent edge policy covering **both** admin pages and every admin API, not only `/admin`. `/api/reviews` shares a public POST with administrative GET/PUT/DELETE; do not block public review submissions inadvertently. Avoid sharing admin accounts. Review account membership and access logs periodically.
4. **Add distributed abuse protection.** In-process limits are per instance, reset when an instance restarts, and are not a strict global or distributed limit. Configure shared edge/WAF or external-store limits for `/api/login`, `/api/send-email`, `/api/add-booking`, `/api/reviews` and pincode lookups; tune thresholds to traffic and monitor false positives and costs. Vercel overwrites the forwarded client IP; on other hosts forwarded headers are ignored unless `TRUST_PROXY_IP_HEADERS=1` is explicitly set behind a proxy that strips and replaces them and cannot be bypassed. A bypassable proxy makes forwarded IPs spoofable.
5. **Configure secrets and data services.** Supply a unique random `SECRET_COOKIE_PASSWORD` of at least 32 characters, TLS-protected `DATABASE_URL` using a least-privilege runtime database account, `RESEND_API_KEY` and `ADMIN_EMAIL` via server-side secret management. Keep migration privileges separate from runtime privileges. Never put credentials in public settings, files, browser bundles, Git or support tickets. Rotate secrets after suspected exposure; rotating the cookie secret signs everyone out.
6. **Set up persistent logo storage.** The upload route accepts only PNG, JPEG, GIF and WebP (3 MB input limit), verifies and re-encodes images as PNG, removes metadata and uses a random name. SVG and PDF are rejected. On production hosts a `BLOB_READ_WRITE_TOKEN` for a **public** Vercel Blob store is required; uploads return an error if it is missing. Public logos are not suitable for sensitive documents. Monitor Blob usage, retention and token permissions; remove old unused logos as needed. `@vercel/blob` is pinned to a version without the currently reported vulnerable transitive dependency and should be periodically reviewed for a safe upgrade.
7. **Preserve existing settings.** Settings are now stored in PostgreSQL; when there is no row, sanitized `data/settings.json` values are initial defaults. A previous serverless filesystem write may not exist in the deployed repository and is **not** automatically recovered. Export and review any real settings before migration. Payment-key inputs were removed because payment integration is not implemented; any real key previously stored there should be rotated and configured only in a secret manager.
8. **Validate real deployment behavior.** In a private Vercel preview with OIDC/BotID enabled and isolated test data, test genuine and automated requests to login, contact, booking and review submission. On Vercel, bots, verified bots, bypassed verdicts and unavailable BotID verification fail closed in deployed builds; WAF bypass rules do not exempt these endpoints. Basic is selected; it is not a substitute for shared rate limiting. Use controlled email credentials and recipients: a real booking/contact test sends email. Check admin login, logout/replay, role changes, moderation, settings, uploads, CSP, cookies, mobile layouts, headers and error paths before any release. No live BotID, Blob, database or email delivery was tested here.
9. **Review browser policies.** Production responses include HSTS, no-sniff, frame denial, referrer and permissions policies and a CSP. The CSP currently permits inline scripts/styles for the Next.js Pages Router, which weakens its XSS protection; move to tested nonce-based CSP if feasible. Test BotID and any third-party integration against the enforced policy. HSTS is not preloaded and does not cover subdomains. Browser defenses do not replace server authorization.
10. **Operational readiness.** Verify database backups and restoration, encryption, network controls, data retention, least privilege and access logs. Enable alerts for repeated failed logins, unusual form traffic and email/Blob volume. Avoid logging message bodies, passwords, tokens or connection strings. Establish security-update, dependency-audit, incident-response and credential-rotation ownership. Check `npm audit` periodically; development-only tooling advisories can remain even when production dependencies report none.

## Request and data boundaries

- Admin mutations, login and logout require a same-origin `Origin` header; scripts using cookie authentication must send the actual site origin. Authenticated responses are private and no-store.
- Anonymous review submissions cannot set publication status, review source or date. Admin approval sets the public flag; rejection or returning to pending clears it. The API's review GET is admin-only.
- Anonymous booking submissions are bounded and validated; their pricing, status and relationships are ignored. All email template fields are escaped and booking IDs are randomly generated with unique-insert retries.
- A booking remains saved if notification delivery fails; the customer is warned not to duplicate the request. This is not a durable email queue. Add an outbox/queue with retry and alerting if guaranteed delivery is required.
- Production file storage and settings require the infrastructure and schema above. Public settings expose only allowlisted branding values; secrets and administrative defaults are excluded.
- Tests use dummy accounts, mocked service calls and synthetic data. A successful local build with a stubbed Prisma engine does not verify a working PostgreSQL connection or migration.
